# COMP 272/400C — Term Project

## Application A — Autocomplete and Spell-Checking Service

This sheet describes one of the three proposed applications. Read it together with the main project handout, which describes the five stages, the deliverables, and the grading.

**Starter code:** project `app-a-autocomplete` — interface `Dictionary`, skeletons `Solution1` and `Solution2`, `DatasetReader`, and the tests `DictionaryTest`.

---

### Scenario

A text editor needs a dictionary service. While the user types, it must:

- flag misspelled words, and
- suggest completions for the word being typed, ranked by how common each word is.

The dictionary is loaded once when the editor starts. Every keystroke can trigger a spell-check and a completion request, so each query must be answered far faster than the user can type.

### Dataset

| Source | Content | Format |
|---|---|---|
| Peter Norvig's word counts, `count_1w.txt` — [norvig.com/ngrams](https://norvig.com/ngrams/) | About 333,000 English words with their frequency in a large web corpus | Plain text, one `word<TAB>count` per line |
| [Project Gutenberg](https://www.gutenberg.org/) books | Free public-domain books, a few hundred KB to several MB each | Plain text (UTF-8) |

- Use the word list as the **dictionary**.
- Use several Gutenberg books as the **query stream** for spell-checking: every word in a book is one lookup. A dozen books give you over a million queries.

**Tips:**

- Convert words to lowercase and strip punctuation before lookup. Decide how to handle apostrophes and hyphens, and document your choice.
- Gutenberg files start and end with a license header and footer. Skip them (look for the lines starting with `*** START OF` and `*** END OF`).

### Functional requirements

The interface `Dictionary` in the starter code is the exact specification; this table summarizes it. Reading the files is done by `DatasetReader`.

| Operation | Description |
|---|---|
| `contains(word)` | Return `true` if the word is in the dictionary. |
| `frequency(word)` | Return the word's count, or 0 if it is not in the dictionary. |
| `complete(prefix, k)` | Return the `k` most frequent words that start with `prefix`, most frequent first (ties in alphabetical order). Return fewer if there are fewer matches. |
| `add(word, count)` | Add a word, or replace its count if it is already present. |
| `remove(word)` | Remove a word; return `true` if it was present. |
| `size()` | Number of words in the dictionary. |

### Non-functional requirements (targets)

Measured with the **full** dictionary, on your machine, with at most **2 GB** of heap (`-Xmx2g`).

| ID | Requirement | Target | Rationale |
|---|---|---|---|
| A-N1 | Average time of `contains` | ≤ 1 µs | A spell-checker re-checks a whole page after each edit: about 500 words must be checked in well under 1 ms. |
| A-N2 | Average time of `complete(prefix, 10)`, prefixes of length ≥ 2 | ≤ 1 ms | One request per keystroke; must feel instantaneous (≪ 100 ms) even with other work to do. |
| A-N3 | Worst time of `complete(prefix, 10)` over all 1-letter prefixes | ≤ 50 ms | Short prefixes match tens of thousands of words; still below the 100 ms "instantaneous" limit. |
| A-N4 | Time to build the dictionary from the full word list (reading the file + `add` of every word) | ≤ 2 s | The dictionary is loaded every time the editor starts. |
| A-N5 | Memory of the dictionary | ≤ 200 bytes per word | The dictionary must stay small next to the rest of the editor. |
| A-N6 | Scalability of `contains` | When the dictionary grows from 10⁴ to the full list, average time grows by at most 3× | The service will later support larger, multilingual dictionaries. |

You may refine these targets or add your own; justify each change in your proposal.

### Workloads to test

- **Real text:** all the words of several books (a realistic mix of very common and rare words).
- **Misspellings:** words **not** in the dictionary, generated by changing one letter of real words (fixed seed).
- **Prefix queries:** prefixes of length 1, 2, 3, and 5, taken from real words. Short prefixes match many words, long ones few.
- **Updates:** a mix of `add` and `remove` (e.g. 10% of operations) during lookups.
- **Sizes:** dictionaries of 10³, 10⁴, 10⁵ words and the full list (take the most frequent n words, or a random sample with a fixed seed).

### Suggested solution pairs

Each solution may come from your team, from class, from a library, or from another source, as long as you explain its implementation and expected performance (see Section 4.3 of the main handout).

| Solution 1 | Solution 2 | Main trade-off to investigate |
|---|---|---|
| Hash table (chaining) | Red-Black tree | Fast exact lookup vs. ordered prefix ranges |
| Hash table (chaining) | Hash table (linear probing) | Same ADT, two implementations; how is `complete` done without key order? |
| AVL tree | Red-Black tree | Stricter vs. looser balance under a read-heavy workload |
| Red-Black tree | Trie *(not covered)* | Ordered tree vs. a structure designed for prefixes; memory cost |
| Hash table + Bloom filter in front | Hash table alone | Does a filter speed up rejecting misspellings? |

### Questions your analysis should answer

- How does a design without key order (a hash table) answer `complete(prefix, k)`, and what does it cost? Does it meet A-N2 and A-N3?
- Which design uses the least memory per word? Is the fastest design worth its memory?
- Does the time of `complete` depend on the prefix length? On the number of matches? Why?
- Is spell-checking real text faster or slower than checking misspellings? Why?
